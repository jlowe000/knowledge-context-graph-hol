# Deploy to the temporary Serverless database

**Version scope:** this existing-target reference describes the published v1 application and its KCV_LAB setup. Use a matching `release` or `v1.0.0` checkout for those scripts. For current dev, preserve the original application and follow the [migration guide](database-migrations.md) and [v2 APEX deployment sequence](../apex/README.md#deploy-the-v2-dev-candidate) in the selected development schema.

This is the existing-target deployment reference. For a new database, use the [beginner walkthrough](fresh-serverless-deployment.md), which includes provisioning, base objects and model setup before APEX.

Deploy the supplied application to the existing temporary ADB Serverless instance, using its existing KCV_LAB schema, working KCV_GENAI profile and loaded public dataset. The local KCV_HOL_TEST workspace/mocks are not the deployment target and must not be copied into the cloud schema.

## Check the target as ADMIN

Run [06_cloud_apex_preflight.sql](../sql/admin/06_cloud_apex_preflight.sql) in Database Actions SQL Worksheet. Record the APEX version, whether the extension objects already exist, and whether ADMIN can create objects in another schema. Do not assume local-container privileges match managed Serverless privileges.

The current app export is generated by APEX 26.1.5. Confirm a compatible target before importing. Installation in an older APEX version requires a compatible build, not editing the release number in the export.

## Create the workspace

After confirming the workspace name is unused, create KCV_KNOWLEDGE mapped to the existing database schema KCV_LAB. This creates the workspace; it does not reset the schema password or create an APEX login account.

<!-- include-sql: sql/admin/07_create_apex_workspace.sql -->

```sql
BEGIN
  APEX_INSTANCE_ADMIN.ADD_WORKSPACE(
    p_workspace=>'KCV_KNOWLEDGE',p_primary_schema=>'KCV_LAB');
END;
/
```

[Script: 07_create_apex_workspace.sql](../sql/admin/07_create_apex_workspace.sql)

<!-- /include-sql -->

Oracle lists ADD_WORKSPACE among the [supported Autonomous Database APEX administration APIs](https://docs.oracle.com/en/cloud/paas/autonomous-database/serverless/adbsb/apex-notes-autonomous.html). If workspace creation is performed through APEX Administration Services instead, select the existing KCV_LAB schema rather than a new empty schema.

## Finish account and application setup

1. Create an APEX app end user using the private-password procedure below, or establish an account through Administration Services. APEX Accounts authentication uses this workspace account; it is separate from the database's KCV_LAB and OCI credentials.
2. Install the [additive scenario extension](scenario-setup.md) as KCV_LAB. Use the same browser's KCV_LAB Worksheet or an appropriately privileged ADMIN session with explicit target schema only after checking privileges. Inspect actual compile errors; do not install the local service mocks.
3. With a separate APEX developer account, import [the app export](../apex/kcv-explorer.sql) through App Builder in KCV_KNOWLEDGE, choose KCV_LAB as parsing schema and allocate a new application ID. KCV_USER is an application end user, not an App Builder developer.
   For a Worksheet-only import, run `python scripts/build_apex_worksheet.py` locally and execute the generated `work/worksheet/20_install_apex.sql` as KCV_LAB. This allocates a new app ID and preserves the engine-generated export; it does not require an App Builder account. Duplicate aliases fail rather than replacing an app.
4. Run the [native acceptance script](../integration-test/verify_scenario_native.sql) as KCV_LAB and then execute the Alex/Casey scenarios in the app using the real model.
5. Record the actual application URL, target versions and validation outcomes privately. Do not commit the temporary database endpoint, passwords or private connection configuration to the public repo.

See [APEX installation details](../apex/README.md) and [scenario validation](scenario-validation.md). Workspace creation alone does not establish that the native graph/model app works; the before/after and source-qualification checks complete acceptance.

## Create the app login through Worksheet

As ADMIN, paste the following block and choose **Run Statement (Ctrl+Enter)**, omitting the final slash. Enter a new password privately in the KCV_APEX_PASSWORD bind dialog and submit it yourself. Do not put the password in SQL text, screenshots, chat or version control. The bind field may display plain text, so keep it out of shared screens. This creates KCV_USER as an app end user without App Builder or SQL Workshop access. It does not reset an existing account.

<!-- include-sql: sql/admin/08_create_apex_app_user.sql -->

```sql
BEGIN
  APEX_UTIL.SET_SECURITY_GROUP_ID(APEX_UTIL.FIND_SECURITY_GROUP_ID('KCV_KNOWLEDGE'));
  APEX_UTIL.CREATE_USER(p_user_name=>'KCV_USER',p_web_password=>:KCV_APEX_PASSWORD,
    p_developer_privs=>NULL,p_allow_app_building_yn=>'N',p_allow_sql_workshop_yn=>'N',
    p_allow_team_development_yn=>'N',p_change_password_on_first_use=>'N');
  COMMIT;
END;
/
```

[Script: 08_create_apex_app_user.sql](../sql/admin/08_create_apex_app_user.sql)

<!-- /include-sql -->

Open the imported application's URL and sign in as KCV_USER. This runtime account does not administer the workspace. Account creation from the KCV_LAB session was rejected on the temporary Serverless instance. The learner created the account successfully through ADMIN SQL Worksheet. Use ADMIN for this administration step; keep the application parsing schema as KCV_LAB. A workspace administrator can alternatively create the end user through Administration Services.
