# Build the APEX application from source

This is the dev maintainer workflow. **Native APEX import/export is part of the application build.** It turns the maintained APEXlang application and generated Supporting Objects into the reviewed installation artifacts. Clean-install and upgrade acceptance then test those artifacts separately.

The maintained source is in Git. Historical `work/` folders, deployed demo data and old application backups are not source inputs. Generated output can live in a new directory outside the repository and outside `work/`.

## Inputs and outputs

| Input | Purpose |
| --- | --- |
| [VERSION](../VERSION), [APEXlang application](../apex/application/application.apx), its pages/shared components and maintained static assets | Product version and authored application |
| [Database manifest](../db/manifest.json), immutable migration payloads and verifiers | Shared schema contract for Liquibase, Worksheet and Supporting Objects |
| [Supporting Objects generator](../scripts/build_apex_supporting.py) | Builds the canonical install/upgrade scripts and their APEXlang definitions |
| [ZIP packager](../scripts/build_apexlang_zip.py) | Packages the native export and verifies scripts, assets and portable metadata |
| [Release builder](../scripts/build_release.py), tracked public summaries and release documentation templates | Produces the consumer distribution after native artifacts are reviewed |

Keep credentials, wallet files, private connection settings and runtime learner data out of these inputs and outputs. Use the [private SQLcl connection setup](dev-connection-setup.md). The application build uses a separately selected owner/workspace and application ID; do not import over the live demo to create a package.

## 1. Select source, tooling and a new output directory

Run from the dev repository root in Oracle Linux/Bash with the documented Python environment and local Java/SQLcl. A container is not required. Review the current source and migration contract before building; do not modify source during generation.

For example, create a disposable build directory outside the checkout:

```bash
KCV_BUILD_ROOT="$(mktemp -d "${TMPDIR:-/tmp}/kcv-build.XXXXXX")"
.venv/bin/python scripts/build_apex.py --check
```

Use a durable external directory instead when retaining a candidate for review. Each generator expects a new destination. A temporary directory is not the final published release location.

The current application targets APEX 26.1. Confirm the actual engine and SQLcl metadata before native import. Follow the [version-matched Oracle skills](oracle-apex-skills.md) and [authoring checks](apexlang-development.md#author-and-validate). An offline validation result does not establish native or browser acceptance.

## 2. Generate Supporting Objects from the database source

```bash
.venv/bin/python scripts/build_apex_supporting.py \
  --transport apex-builder --output "$KCV_BUILD_ROOT/supporting"
.venv/bin/python scripts/build_apex_supporting.py \
  --transport apex-builder --output "$KCV_BUILD_ROOT/supporting" --check
```

Keep the complete generated directory, including `manifest.json`, canonical SQL and transport metadata, for verification. During the v2.1.0 source review, all 221 files regenerated byte-for-byte against the reviewed canonical input. This was a regeneration comparison, not a new database installation test. Later source changes can change the file count and hashes.

## 3. Assemble the application for native compilation

Create a clean copy of the maintained application and add only the generated APEXlang Supporting Objects subtree:

```bash
cp -R apex/application "$KCV_BUILD_ROOT/application"
cp -R "$KCV_BUILD_ROOT/supporting/supporting-objects" \
  "$KCV_BUILD_ROOT/application/supporting-objects"
```

The full canonical directory remains separate. Do not add research extracts, old test fixtures, the complete repository, or the canonical SQL inspection tree to the application archive.

The authored application does not contain `.apex/apexlang.json`; prepare the native compiler metadata in this temporary assembled directory for the confirmed target version. The reviewed 26.1 export used `mmdVersion` `26.1.0+3102`. Do not use a newer metadata default just because the local SQLcl version offers it. Native deployment metadata must describe the selected build target and remain private until the ZIP packager removes environment-specific fields. Do not invent a source application ID or copy an old workspace's settings.

## 4. Compile/import in the isolated build workspace

Use the platform, owner and workspace preparation in the [dev installation guide](fresh-dev-deployment.md), then stop before that guide's application import and runtime setup. Install the matching static schema through the [migration workflow](database-migrations.md) when backend checks require it; an empty prepared owner was sufficient for the earlier definition-only import/export rehearsal. Record the intended application ID and confirm whether the operation creates a new app or deliberately replaces an existing build app.

Validate the assembled application against that workspace's metadata. For this application-only build import, disable automatic Supporting Objects execution in the same authenticated SQLcl session:

```sql
BEGIN
  APEX_APPLICATION_INSTALL.SET_AUTO_INSTALL_SUP_OBJ(FALSE);
END;
/
```

Then use native `apex import` with the assembled directory and explicit workspace, schema, application ID and alias, following the [native import example](fresh-dev-deployment.md#6-validate-and-import-a-new-apex-application). Substitute the actual build target and assembled path; SQLcl does not automatically expand the Bash variable above. Inspect native errors and the resulting app identity, pages and assets. Check that this application-only operation did not execute backend installation scripts or change existing data.

This step compiles the application definition and registers its Supporting Objects for export. It does not prove that those scripts can install or upgrade a learner environment. Model credentials, public collection loading and learner readiness belong to the later installation tests.

## 5. Export the native build artifacts

Use the same reviewed build application for both exports. The following are SQLcl command templates; replace the application ID and absolute output paths before running them:

```text
apex export -applicationid <build-app-id> -exptype APEXLANG -expsupportingobjects Y -skipexportdate -dir <native-export-directory>
apex export -applicationid <build-app-id> -expsupportingobjects N -skipexportdate -dir <sql-export-directory>
```

The APEXlang export includes Supporting Objects. The SQL export is definition-only for the SQL-first route, whose schema installer runs separately. Do not hand-edit the engine-generated SQL or pretend a ZIP of the authored source is the reviewed native export.

Inspect the native application directory, including its `.apex` and deployment metadata. Select that exact exported application directory as the ZIP source, not its parent export directory.

## 6. Package and validate the ZIP

Set `KCV_NATIVE_APP_DIR` to the actual application directory returned by the native export, then run:

```bash
.venv/bin/python scripts/build_apexlang_zip.py \
  --source "$KCV_NATIVE_APP_DIR" \
  --output "$KCV_BUILD_ROOT/dist/kcv-explorer.apx.zip" \
  --expected-assets apex/application/shared-components/static-files \
  --canonical-candidate "$KCV_BUILD_ROOT/supporting"
```

The packager checks the canonical install/upgrade drivers, static assets, flat archive layout and native ZIP safety limits. Its default public alias is `KCV-EXPLORER`. It retains the reviewed native source application ID while removing private deployment settings. Keep the default privacy behavior; `--include-deployments` is for private reproduction only.

Run native validation of the produced ZIP and inspect the results. Record the actual source, version, canonical-manifest and export hashes in the [SQL export receipt](../apex/export-validation.json) and [APEXlang receipt](../apex/apexlang-export-validation.json) only after their stated checks pass. The packager's manifest starts with native/browser validation pending; it is not a passing acceptance receipt. A new export can have different native identifiers or bytes even when the authored source is unchanged. Do not reuse an old positive receipt for different bytes.

Keep the reviewed definition-only SQL export at [apex/kcv-explorer.sql](../apex/kcv-explorer.sql), as required by the release builder. Review it with the receipt rather than modifying generated SQL manually.

## 7. Build and test the consumer package

After the native exports and matching receipts are reviewed, the release builder accepts arbitrary explicit input/output paths:

```bash
.venv/bin/python scripts/build_release.py \
  --output "$KCV_BUILD_ROOT/release" \
  --apexlang-zip "$KCV_BUILD_ROOT/dist/kcv-explorer.apx.zip" \
  --apexlang-receipt apex/apexlang-export-validation.json \
  --apexlang-canonical "$KCV_BUILD_ROOT/supporting"
```

Follow the [packaging plan](apex-led-release-packaging-plan.md) for the separate APEX-led and SQL-first clean/upgrade acceptance routes, preserved-data checks, package review and publication gates. Import/export success alone does not establish Supporting Objects installation, model connectivity, learner behavior or migration preservation. Reusing an already reviewed same-version ZIP is valid only when the current source/receipt/hash checks still match.

For normal installed-app credential and model configuration, use [owner binding and Deployment setup](deployment-owner-binding.md). Private runtime configuration is not baked into the ZIP. Creating a build artifact neither promotes release nor commits, pushes or tags anything.

## Current automation and cleanup boundaries

Supporting Objects generation, static-asset checks, native ZIP packaging, Worksheet wrappers and release packaging have maintained scripts. Native compilation/import/export is an established build stage, but a single maintained Bash command coordinating the whole sequence does not yet exist. Target selection, temporary metadata preparation, native execution and receipt recording still need explicit orchestration. This guide does not claim a newly rehearsed end-to-end build from an empty checkout.

Old APEX staging directories and backups can be removed after required outputs are reproduced or retained and no process is using them. Generated artifacts do not replace the versioned application or immutable migration source. Tool caches and private saved connections have separate lifecycles; keep the active tools, shared wallet and authorised connections during build-output cleanup.

The **full release/data build** still has a separate local provenance dependency: [validate_summary_basis](../kcv/editorial.py) reads `work/catalog-passages.json`. The public summaries are tracked, but this extracted evidence is checked before packaging. Retain or regenerate it through the [content pipeline](content-pipeline.md); choosing external output paths does not remove that input dependency. Raw authoring tests also use `work/passages.json` and pinned source editions. These inputs are not part of the APEX application ZIP and must not be published as build output.
