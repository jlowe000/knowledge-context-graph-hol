## Outcome and scope

Provide an end-to-end beginner path from **OCI ADB Serverless provisioning**, through administrator/schema preparation and **APEX workspace creation**, to installation and learning. The primary application deliverable is one **APEXlang application ZIP** that a workspace installer uploads directly through **App Builder → Import**, installs with Supporting Objects, and finishes through guided configuration. After the documented administrator preparation, application installers should not need to unpack the archive, copy backend SQL, install Python/SQLcl/Liquibase, or understand package compilation. A prepared-environment shortcut starts at ZIP import after verifying the same prerequisite checkpoints.

The three experiences share one application, ontology, schema contract and public dataset:

- **APEX-led:** guided provisioning/preparation, ZIP installation and use, with explicit administrator handoffs and a prepared-environment shortcut.
- **OCI / DBA-led:** SQL-first deployment and validation for technical participants who want the working outcome first.
- **DEV-led:** adaptation and developer workflow first, including APEXlang, SQLcl/Liquibase, source preparation and tests.

This plan implements the first experience without replacing the other two. After acceptance and separately authorised promotion, release can offer APEX-led and OCI / DBA-led installation; dev retains the developer experience. No third branch is needed. Clean installation and migration are lifecycle choices within an experience, not additional experiences.

In scope are the documented human steps to provision ADB within an authorised OCI tenancy, prepare capabilities/schema/grants/credentials, create and enable the APEX workspace, and establish installer access. Out of scope: creating an OCI tenancy, automatic Java enablement/restart from the application, granting privileges from the application, providing model access or usage funding, oracleapex.com compatibility, a second application/data model, auto-ontology, the learning-loop epic and the Explorer-evaluation epic. Those two future epics remain separate from deployment and My Contexts.

Document two preparation outcomes: **environment ready for application installation** and **application ready for learners**. The full guide includes the OCI and ADMIN steps leading to the first outcome. An administrator can instead supply that prepared environment so participants can take the shortcut and learners do not need their own OCI accounts. ### APL-01 — Prove APEX execution identity and capability boundaries

This is the first execution-identity implementation gate. Use a new isolated `KCV_V<major>_<build>` schema/workspace, following the [build lifecycle](dev-build-lifecycle.md). For a clean browser installation, choose **Auto Assign New Application ID** unless the facilitator has reserved an ID for that workspace; record the resulting application identity for verification. An absent `APEX_APPLICATIONS` row does not establish reservation availability. A supported upgrade retains its existing ID. Do not overwrite or retire the existing deployment to create this test target.

- Exercise a minimal real Supporting Objects import and record its effective schema, execution identity and accessible direct grants privately. Test both App Builder installation and authenticated setup-page execution; they are different execution contexts.
- Confirm that native RDF creation/querying, DBMS_CLOUD loading, profile/agent registration and scoped compilation can run under the intended owner without ADMIN privileges. Test actual access; do not rely on synonyms or another owner's credential.
- Measure script/request size and duration limits with representative migration payloads. Keep dictionary checks targeted to required project objects; do not reuse the broad joined metadata probe that stalled in the hosted-service investigation.
- Choose a trusted installation transport after those results. Current wrappers require `SESSION_USER = CURRENT_SCHEMA`; do not remove these guards globally, pretend `ALTER SESSION SET CURRENT_SCHEMA` is an owner login, or rewrite published payloads to bypass them.
- Where a narrowly scoped installer API is necessary, bind it to the verified application schema, approved migration IDs/hashes and authorised installer. It must not accept arbitrary SQL, arbitrary schemas, browser-supplied identities or unrestricted object names. Ordinary app users and another workspace must be denied.

**Exit:** a recorded proof of the authorised APEX path and its limits. If a core operation still requires an external owner session, keep that explicit in the administrator preparation contract or revise the design before claiming browser-only installation. Do not conceal the gap in a success screen.

### APL-02 — Generate installation, upgrade and compilation scripts

- Extend the build pipeline to emit ordered Supporting Objects from the existing manifest and frozen payloads. Retain dependencies, checksum verification, project migration receipts and physical postconditions; do not fabricate Liquibase ledger rows for an APEX installation.
- Introduce any new installer state/packages as new versioned migrations. Keep application version, migration version, dataset version and package hash separately identifiable. Do not reserve a new product tag or edit historical validation records during planning.
- Implement pre-installation checks for the supported target, empty vs supported existing schema, privilege readiness and storage. Refuse unknown/customised/newer contracts rather than choosing a destructive fresh install.
- Compile specifications and bodies in dependency order. Inspect required object validity and compiler errors before recording completion; recompile only relevant project objects. Compile warnings/errors must remain diagnosable without exposing source secrets.
- Keep a small bootstrap/readiness surface usable when application tables/packages are not yet installed. Normal learner pages must remain unavailable until the required contract is ready.
- Generate the APEXlang application ZIP with supporting definitions and application static assets included, and verify that those definitions survive the native import/export round trip. Source files or a successful SQL export alone do not prove that the downloadable ZIP imports through App Builder.

**Exit:** reproducible, inspected application ZIP containing complete clean/upgrade support scripts and postconditions, with no unpacking or command-line step required by its installer. A fresh installation and a no-change verification/retry must not create duplicate objects or receipts.

### APL-03 — Add administrator setup and runtime configuration

- Implement the setup UI in APEXlang, with server-side authorisation for every page, process and callback. Installer privileges must be separate from ordinary app-only accounts. Hiding navigation is not authorisation.
- Validate model name/region/compartment and the selected schema-local credential. Retain the administrator-prepared route and resource-principal preparation; resource-principal IAM/dynamic-group prerequisites stay in the administrator guide.
- Add the separately authorised **Create a local OCI signing credential** form for a native workspace administrator bound to this application and owner. Accept only the user OCID, tenancy OCID, fingerprint and matching unencrypted base64 key body (submitted field maximum 4,000 bytes). OCI key registration and IAM permissions remain external prerequisites. Create fixed owner-local `OCI_USER_CRED` only when absent; never drop, overwrite, rotate or grant a credential through this action.
- Pass private inputs as transient binds outside journal JSON and input hashes. Keep them out of exports, page defaults, app settings, URLs and diagnostics. Use native Password items with per-request storage, explicit clearing and sanitized errors. Verify actual session/debug/audit behavior using synthetic canaries; request-only storage and app-level debug settings do not establish a universal no-logging guarantee.
- Reuse exact server-side identity/binding checks, the setup/admission locks and maintenance handling. Reject an existing credential before journal/readiness changes; successful replay acknowledges the recorded creation without comparing or storing a secret hash. Invalidate the model test before native creation. A partially completed creation must retain the credential, remain paused and require review, without automatic recreation or inference.
- Make RDF network and agent/team setup explicit, repeatable and owner-scoped. Upgrades preserve existing conversations and unrelated objects. Use the current grounded-answer registration; optional extraction teams remain optional.
- Make model testing an explicit action, record its outcome and avoid repeating inference merely when a page refreshes or a saved conversation reopens.
- Keep account provisioning a workspace-administrator responsibility; the package must not distribute a shared learner password. Separate individuals need separate app identities.

**Exit:** an authorised installer can complete runtime configuration through the supported path, while a learner or cross-workspace caller cannot invoke setup, read configuration secrets or alter another installation.

### APL-04 — Guide GitHub loading and graph construction

- Preserve the preferred GitHub dataset path: the application includes its loader and an approved full commit SHA/manifest hash; public data is fetched during setup. This is one application download, not an offline bundle. Never silently follow a moving branch head.
- Keep the existing checks for public sources, content hashes, graph scope and staging/activation. Ship public metadata and attributed summaries only; no source PDFs, extracted working text, personal contexts or private research endpoints are captured in the export.
- Show bounded phases for fetch, verification, source/passage loading, RDF construction and activation. Use measured bounded requests or a separately proven worker mechanism; do not assume scheduler privileges or a long browser request will survive.
- Represent ontology/data as portable definitions and triples, rebuilding native graph storage in the target owner. Use existing native APIs and verification rather than exporting physical graph internals.
- Preserve the prior active collection on failure. An upgrade does not automatically refresh its dataset or republish personal revisions. Retry must inspect recorded state and hashes before resuming.
- Address optional local embeddings explicitly. Initially the facilitator may install the approved model through the existing owner route; a browser-enabled alternative needs a new authorised API and separate testing. Do not relax the existing APEX exclusion globally. Display keyword fallback honestly when that optional model is absent, and require native VECTOR capability in either mode. Do not embed the model binary in the public app export.

**Exit:** the same approved public dataset yields the verified expected source/passage/triple counts and usable graph evidence. GitHub denial, failed hashes, interrupted graph creation and optional-model absence each have a clear, recoverable outcome.

### APL-05 — Preserve clean/upgrade semantics and recover interrupted work

- Use APEX's existing-supporting-objects detection only to route the user. Independently verify the actual baseline, physical schema, receipts and installed source before mutation; a table name alone is insufficient.
- Support a clean isolated schema and upgrade from the published v2.0.0 contract. Keep the documented v1 adoption/migration route available and test it separately if exposed in the APEX wizard. If v1 cannot be safely supported there initially, route it explicitly through the tested SQL-first migration instead of presenting an untested APEX option.
- Retain the existing schema/workspace, application ID/alias, app accounts, credentials, settings, graphs and personal history during upgrade. Dataset refresh and optional model replacement are distinct explicit operations.
- Coordinate the app-definition replacement with schema/runtime upgrade in a maintenance window. App Builder can replace pages before supporting scripts finish; incompatible learner pages must not run during that interval or after a failed upgrade. Verify this gate with existing authenticated sessions.
- Record phase/step identity, expected hashes and outcomes. Define locking and interrupted-operation recovery so a second installer, refreshed browser or repeated request cannot apply the same step concurrently.
- Never describe database DDL/RDF operations as one reversible transaction. A restored APEX export alone is not a database rollback. Define safe forward recovery and a verified pre-upgrade backup/restore route; never delete learner work to make a retry pass.
- Deinstallation, if offered, must explicitly identify destructive scope, require administrator confirmation, preserve unrelated objects and leave JAVAVM enabled. It is not a recovery shortcut.

**Exit:** clean and upgrade paths pass independently, preserved-work comparisons pass, and interruption/retry cannot cause false completion or loss of an active collection or private history.

### APL-06 — Validate the experience and prepare future release packaging

- Add narrowly scoped generator/contract tests for payload order, hashes, script boundaries, supporting-object completeness, upgrade detection and prerequisite rejection. Test changed behaviour rather than mirroring generated strings alone.
- Rehearse the exact downloadable ZIP, uploaded intact through App Builder on isolated ADB targets, including a clean install, v2 upgrade, interrupted/repeated install and the intended public GitHub load. Include the archive's hash and actual ORDS/REST-schema readiness in the acceptance record. Repeat the relevant SQL-first and dev migration checks so the new transport does not diverge from them.
- Exercise a real grounded answer, its sources and lineage, personal context refinement/adoption, follow-up and sign-in persistence. Existing validation can guide these tests but cannot be relabelled as an APEX-led pass.
- Exercise two separate learner accounts plus an installer account. Verify private context/history isolation and rejection of learner calls to setup endpoints. Test upgraded users with existing sessions and saved evidence.
- Export again after private runtime configuration and inspect the app, support scripts, static assets and diagnostics for secrets, personal rows and environment identifiers. Test that setup errors/debug output do not capture credentials.
- Run a beginner review from OCI ADB provisioning and workspace creation through the downloaded ZIP, guided setup and learner handoff. Separately exercise the prepared-environment shortcut. Document screenshots/clicks, expected outcomes, recovery and actual administrator handoffs; use safe screens without credentials, login details or environment URLs. An existing-database rehearsal does not satisfy the new-database provisioning/Java activation part of acceptance.
- Record exact code/package/dataset hashes, APEX/ORDS/database versions, prerequisite preparation, test scope, failed/pending cases and preservation evidence. Public records use neutral labels; keep live endpoints and private audit details outside Git.

**Exit:** evidence supports the stated beginner path, with honest boundaries. Only then propose updates to `release-docs/`, the release builder and curated distribution. Do not promote release or change tags without the user's separate instruction.

## Acceptance matrix

| Scenario | Required result |
| --- | --- |
| New ADB and new APEX workspace | Beginner follows OCI provisioning, ADMIN capability/schema/grant/credential preparation, workspace creation/enablement and both installer login paths before ZIP import; record new-database and any Java activation/restart results explicitly |
| Facilitator-prepared environment | Beginner verifies phases 1–3 and starts at ZIP import without creating duplicate databases, schemas/workspaces or resetting accounts/credentials |
| Prepared empty ADB schema | Upload the application ZIP intact through App Builder; supporting-object creation/compilation, setup and a real evidence-backed question pass without installer shell, unpacking or manual SQL |
| ZIP import prerequisites unavailable | Identify the missing ORDS version or REST-enabled workspace schema before import; return to administrator preparation without describing a SQL-file import as the ZIP acceptance result |
| Missing Java/native API/grant/quota or unsupported engine | Named prerequisite failure before schema mutation; no self-grant or Java enablement |
| Known v2 installation | Same-ID upgrade; schema verification and preserved data/graph/history/account comparisons pass |
| v1, modified or newer installation | Supported explicit route only; no guessed baseline or fresh-create overwrite |
| Repeated import/setup and concurrent installers | Verified completed steps retained; safe lock/retry behaviour; no duplicate registration or data activation |
| Interrupted schema/app/runtime step | Recorded failure/pending state; app remains gated; documented verified recovery |
| GitHub failure or changed dataset checksum | No unverified activation; existing collection remains usable after recovery |
| Missing/invalid model permission | Setup remains incomplete with a clear administrator action; no false model-ready status |
| Installer credential creation | Approved absent-name creation succeeds locally; stored name is fixed; no model call; recorded model test invalidated; explicit profile test required |
| Existing credential, replay or concurrent creation | Existing credential is unchanged; a completed token acknowledges only its recorded action; new-token duplicate rejected without state changes; concurrent attempts serialize |
| Credential validation, authorization or post-creation failure | Private inputs cleared with safe errors; unauthorized caller changes nothing; partial success never triggers replacement/retry and keeps learning paused |
| Credential privacy | Synthetic canaries absent from rendered responses, persistent session state, inspected debug/audit outputs, journals and re-export; inspect normal and developer LEVEL9 paths before real-key entry and record platform limits |
| Optional embedding model absent | Clearly labelled keyword search works; native VECTOR prerequisite still enforced |
| Learner, installer and second learner | Setup authorisation and account isolation hold across UI, callbacks, evidence and history |
| Export after runtime use | No keys/passwords/credential values, private data or environment identifiers in distributable artifacts |
| Existing SQL-first and dev routes | Same target schema/evidence contract, valid migration receipts and relevant regressions pass |
