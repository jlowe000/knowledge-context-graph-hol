## Keeping the ZIP importable

The first full native directory import/export passed, but its ZIP failed native SQLcl 26.3.1 validation. That bundled APEXlang implementation enforces maximum unpacked sizes of 10 MiB per entry and 30 MiB per archive. The initial installation and upgrade drivers exceeded those limits. Compression of the outer ZIP alone cannot reduce its unpacked entry sizes. Do not increase the importer safety limits or describe directory import as proof of ZIP acceptance.

The candidate uses lossless gzip/Base64 transport for fixed, generated SQL steps inside the same guarded driver. This is packaging, not encryption or a new source of migration logic. Keep the plain SQL step artifacts and their hashes available for review. Each decoded step must match its declared byte count and SHA-256 before execution; conversion from UTF-8 to a CLOB must succeed without a warning and reproduce the same bytes on round-trip. Verify the compressed bytes before decompression as well. No learner-supplied compressed data is accepted by this transport.

Oracle documents gzip compatibility and caller responsibility for temporary LOB cleanup in [UTL_COMPRESS](https://docs.oracle.com/en/database/oracle/oracle-database/26/arpls/UTL_COMPRESS.html). Verify execution access to `UTL_COMPRESS`, `UTL_ENCODE`, `DBMS_LOB` and `DBMS_CRYPTO` under the effective parsing owner before installation. In the isolated ADB rehearsal, the compression/encoding packages are executable through PUBLIC and DBMS_CRYPTO is directly granted. Do not assume the presence of a synonym establishes execution access on another service.
